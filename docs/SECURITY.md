# Безопасность

Это инженерный чек-лист, не юридическая консультация.

## Аутентификация

- Better Auth, email + пароль, минимум 8 символов.
- Пароли хешируются адаптером Better Auth; в приложении нет собственного хранения паролей.
- Сессия — HttpOnly cookie, 30 дней, обновление раз в сутки.
- В production требуется подтверждение email.
- Сброс пароля одноразовый, срок действия — 1 час.
- Роль `admin` — additional field с `input: false`; клиент не может назначить её себе.
- Origin проверяется Better Auth; `trustedOrigins` ограничен публичным URL и мобильной схемой (`APP_MOBILE_ORIGIN`).
- Мобильный клиент использует `@better-auth/expo` и тот же Better Auth; токен хранится в SecureStore.

## Авторизация

| Endpoint | Требование |
| --- | --- |
| `/api/progress` | сессия |
| `/api/user-mnemonics` | сессия, доступ только к своим записям |
| `/api/mobile/sync` | сессия + активная VIP-подписка |
| `/api/privacy/contribution-preference` | сессия, только своя настройка |
| `/api/mnemonic-contributions/batch` | сессия + серверное согласие `granted` |
| `/api/mnemonic-contributions/withdraw` | сессия, только свои вклады |
| `/api/admin/mnemonic-contributions*` | `role = admin` |
| `/api/billing/create-payment`, `/api/billing/status` | сессия |

- Каждый запрос прогресса, ассоциаций, согласия, вкладов и платежей фильтруется по `userId` из сессии, а не из тела.
- Тело запросов описано строгими Zod-схемами; `userId` и media-поля отклоняются.
- VIP проверяется на сервере через `hasVip`; клиентская проверка — только UX.
- Согласие на вклады проверяется на сервере при каждом batch; без `granted` — `403`.

## Платежи

- Сумма и срок берутся только из серверного `plans.ts`.
- VIP активирует только webhook ЮKassa.
- Return URL не считается подтверждением оплаты.
- Webhook идемпотентен: повторный `payment.succeeded` не создаёт вторую подписку.
- `Idempotence-Key` уникален для каждого платежа.
- Рекомендуется включить allowlist IP ЮKassa.
- Секретный ключ ЮKassa не передаётся в браузер.
- Текущие ограничения и расхождения с документацией ЮKassa описаны в [BILLING_YOOKASSA.md](BILLING_YOOKASSA.md).

## Личные ассоциации и изображения

- Личные ассоциации принадлежат владельцу сессии; чужие id возвращают `404`.
- Удаление — tombstone с `rev`; старый снимок не воскрешает запись.
- Изображения только локальные: mobile document directory, web IndexedDB.
- В sync/contribution/logs нет файла, URI, имени, base64, MIME, размеров и EXIF.
- Входные изображения проверяются по MIME, размеру, пикселям и magic bytes; SVG/GIF и подделка сигнатуры отклоняются; результат перекодируется в JPEG.
- Текст ассоциаций хранится как текст и никогда не рендерится как HTML.

## Согласие, модерация и псевдонимы

- Согласие добровольное, без предустановленных галочек; статусы `unset/granted/declined/ask_later/withdrawn`.
- `ask_later` откладывает повтор на 30 дней и три создания; `withdrawn` останавливает отправку.
- Подозрительный текст (email, телефон, URL) не блокирует отправку, но помечается `sensitive_content:*` и остаётся `pending`.
- `approve` означает «одобрено для ручной редактуры», а не публикацию.
- `withdrawn` терминален: последующие решения возвращают `409`.
- Псевдоним автора — HMAC-SHA256 от `userId` с `MODERATION_PSEUDONYM_SECRET`.
- В production обязательно задайте отдельный случайный `MODERATION_PSEUDONYM_SECRET` (≥32 символа). Без него используется `BETTER_AUTH_SECRET`, а в development — небезопасный fallback. Смена секрета меняет все псевдонимы.
- Email и сырой `userId` не возвращаются в очередь модерации.
- Решения фиксируются в `mnemonic_contributions` и `audit_log`.

### Ограничения rate limit

- Batch вкладов: 30 запросов на пользователя в час.
- Счётчик хранится в памяти процесса и сбрасывается при рестарте/деплое.
- Несколько инстансов не разделяют счётчики; для строгого распределённого лимита нужен Redis или счётчик в PostgreSQL.
- Отзыв вкладов отдельным rate limit не ограничен.

## Данные

Собираем минимум:

- email, имя;
- progress: wordId, FSRS-параметры, выбранная ассоциация;
- отзывы: оценка, факт подсказки, время;
- личные ассоциации: текст и ids, без изображений;
- вклады: текст и ids при явном согласии;
- платежи: сумма, статус, идентификаторы провайдера.

Не собираем без необходимости:

- адрес, телефон, паспортные данные;
- платёжные реквизиты карты (ими владеет ЮKassa);
- изображения и метаданные файлов пользователя.

## Логи

- Не логировать пароли, токены сброса, cookie и секреты.
- Не логировать `sceneText`, `cueWord`, media URI, содержимое sync/contribution payload и тела запросов.
- Ошибки новых API логируются статической меткой без объекта ошибки: параметры Drizzle/Postgres не попадают в лог.
- В development письмо логируется с маскированным получателем, без ссылки и токена.
- Ошибки Resend логируются с усечённым и отредактированным ответом; ошибки ЮKassa — с усечённым ответом провайдера.
- Перед production настроить срок хранения логов и доступ.

## Security headers и CSP

`next.config.ts` задаёт для всех маршрутов:

- `X-Content-Type-Options: nosniff`;
- `X-Frame-Options: DENY`;
- `Referrer-Policy: strict-origin-when-cross-origin`;
- `Permissions-Policy: camera=(), microphone=(), geolocation=()`;
- `Cross-Origin-Opener-Policy: same-origin`;
- `Strict-Transport-Security: max-age=31536000; includeSubDomains`.

CSP пока не настроен. Причина: Next.js App Router использует inline-скрипты гидратации, а `cacheComponents`/`partialPrefetching` усложняют nonce-политику; непроверенная CSP ломает загрузку. Это осознанный follow-up: внедрять CSP через nonce/middleware с e2e-проверкой, а не вслепую.

## Известные ограничения

- Нет OAuth и 2FA.
- Нет автоматического удаления аккаунта через UI.
- Нет защиты от распределённого брутфорса beyond Better Auth rate limit.
- Нет CSP; базовые security headers заданы в `next.config.ts`.
- Rate limit вкладов не распределён между инстансами.
- Нет физической очистки tombstone-строк и withdrawn-вкладов.
- Нет аудита всех действий пользователя, только активация подписки и решения модерации.
- Webhook ЮKassa не перепроверяет статус платежа через GET API; рекомендуется IP allowlist.
- `YOOKASSA_TRUSTED_IPS` сравнивает точные адреса, а официальные диапазоны ЮKassa включают CIDR.
